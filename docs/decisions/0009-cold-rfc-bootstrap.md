# Cold RFC bootstrap and first publication

The collector and rate-budget discussion below describes the historical
dual-queue design. The HTTPS-first decision supersedes its proposed source
policy and retains the cold-start timing contract. [HTTPS-first RFC synchronization](0010-https-first-rfc-synchronization.md)

Phase 0 measures the current collector and defines the acceptance gate for the proposed dual-queue collector. The implementation baseline is `db38619e8b3011b0e93aa5e7ec9e3b6928e2ab72`, which already overlaps some HTTPS and parsing work, commits in RFC order, and preserves NUL-containing TXT in bytes mode. The earlier serial and bounded-pipeline results end at a ready candidate. [Implementation status](../implementation-status.md#bounded-reconciliation-pipeline)

## Timing contract

**T0** is immediately before the documented fresh-stack initialization starts on a pre-provisioned Compose host with empty PostgreSQL and mirror volumes. Start with volume ownership, then PostgreSQL first-time initialization, roles and passwords, bootstrap, migrations and storage checks. Run the daemon’s full acquisition, parsing, source verification, indexing, candidate checks and promotion. Include service startup and real acquisition connection setup. [Fresh-stack initialization](../deployment.md#initialize-or-upgrade)

**T1** is the first observed probe pass where PostgreSQL shows the full catalog-selected generation as active and published at sequence 1, Serve’s loopback `/ready` returns 200, and a pinned-protocol MCP `get` returns original bytes from the same generation and sequence. Record publication commit, readiness, MCP read and authenticated outbox delivery separately. A trial requires successful delivery. If it follows T1, also report the elapsed time through delivery. Use a monotonic clock for elapsed times and UTC for correlation. Polling contributes to the observed T1.

Report image build, import or pull, infrastructure DNS/TLS setup, and manual secret provisioning separately from T0–T1. The primary baseline uses preloaded OCI images. A cold database and mirror are independent of the image cache state. Record the pull source and cache state when a cold pull is measured.

## Proposed collector

- Capture the starting catalog and bind both producers to its selected RFC IDs. A single official rsync session populates a bounded private mirror work tree. Only finalized snapshots enter the TXT parser. The independent HTTPS producer schedules RFCXML immediately, using a single request-start limiter shared with both catalog requests and any strict TXT checks. Set in-flight concurrency separately from pacing. Bound raw and decoded bytes, queue items, durable staging, workers, retries, child lifetime and cancellation.
- Join results by RFC ID and catalog capture. One coordinator owns short PostgreSQL writes and may persist sealed TXT before XML settles. Retain compact results and durable blob references while either side waits. Validate exact membership, terminal XML outcomes under the existing coverage rules, ending catalog agreement, and deterministic manifest content before readiness. Preserve original bytes, zero-based half-open ranges and parser/index versions. XML 404 and 410 mean unavailable. Malformed or unsuccessful requests carry their own evidence and affect coverage. Missing required TXT, catalog drift, or failed validation aborts the candidate. Cancellation, worker failure, or storage failure stops admission, reaps child processes, and leaves recoverable work under the corpus fence.
- Use official-rsync TXT as the future default while preparing the first full publication on a fresh store at sequence zero. The BLAKE3 digest binds stored bytes to the rsync capture. The strict dual-source policy also requires a matching body from TLS-authenticated HTTPS and is available from the start. After first publication, require that comparison for new or changed TXT. Eligible unchanged TXT can reuse its actual prior proof after verifying current selected membership, staged bytes, canonical digest and policy compatibility. Record the observed rsync URL and the verification actually performed. Preserve historical observation identities and quarantine conflicting bytes.
- Select the policy under the corpus fence for the entire run. Use the same engine for automated and manual reconciliation. The manual command freezes a candidate and the daemon promotes via the existing atomic pointer and notification outbox. Roll out behind a validated policy selector and rehearse on fresh and existing stores. Roll back by draining Sync and selecting strict verification. Reverting binaries requires schema compatibility, or a verified backup and restore. Preserve the published generation and original proofs across policy changes.

## 900-second gate

Use 90 seconds each for fresh-stack initialization and final validation, promotion and readiness. In the remaining 720 seconds, a planning corpus of 9,861 RFCs needs 13.7 TXT documents indexed per second and about 13.7 HTTPS starts per second for one RFCXML request per selected RFC and two catalog requests, before retries. If strict cold TXT verification is required, the same acquisition window needs about 27.4 total HTTPS starts per second.

The current one-second start interval makes the XML-only HTTPS plan infeasible for 900 seconds. The 9,863 starts are at least 9,862 seconds apart from first to last (2 h 44 min 22 s). Strict cold TXT verification adds 9,861 starts and raises that floor to 19,723 seconds (5 h 28 min 43 s). These are lower bounds before final responses and downstream work. Additional concurrent workers cannot change the start-spacing floor.

Retain one-second pacing until provider policy and permission support a measured faster profile. RFC Editor documents official bulk TXT via `rfcs-text-only`. An alternative XML bulk adapter requires evidence that the official dataset carries equivalent authoritative RFCXML originals and the operator’s approval. A private fixture result conveys neither upstream permission nor production throughput. [RFC Editor download documentation](https://www.rfc-editor.org/series/rfc-download/)

The proposed starting budget is the current Compose envelope. Sync has 2 CPUs, 2 GiB RAM and a 512 MiB scratch mount. Serve, Sync, Feed and PostgreSQL total 6.5 CPUs and 3.875 GiB of service memory limits. Use 8 vCPUs, 8 GiB RAM and 32 GiB working disk as a provisional benchmark budget with host and proxy headroom. The accepted-input cap is 4 GiB. Reserve separate persistent space for the future rsync work tree, canonical objects and PostgreSQL/WAL. Revisit these budgets after a representative corpus-scale run.
